# Multi-Agent Workboard v2.1 — 規格(權威版)

> 擁有者:Claude(架構/整合)。其他 agent 施工前必讀本檔 + `AGENTS.md`。
> 輸入來源:`docs/Multi-Agent_Workboard_v2_實作與功能建議.md`(以下簡稱「v2 建議書」)+ 現況盤點(見 §1)。
> 本檔與 v2 建議書衝突時,**以本檔為準**;要改本檔須在對應 WP 任務卡的 Log 寫明原因。

## 0. 一句話目標
按下「開始」後可以離開;回來時一眼知道:誰在做什麼、做到哪、有沒有卡住、要不要我決定。
並且 **agent 動手改檔之前,一定先給我看計畫、我核准才執行**。

## 3. 架構決策(不可擅自改)
1. 維持 **Node 內建模組、零依賴**;不引入 npm 套件、不改 Python。
2. **檔案即資料庫**:所有狀態是可讀檔案(§4),不加資料庫。
3. **唯讀解析各 CLI 的 log**,不改它們的設定。
4. **絕不使用** `--dangerously-skip-permissions` / `--dangerously-bypass-approvals-and-sandbox`。
5. 即時串流用 **SSE**(Node `http` 即可),不用 WebSocket。
6. 前端仍是 `web/` 底下的原生 HTML/JS(不引入框架/打包)。單檔過大時可拆成多個 `web/*.js` ES module。
7. 每個 WP 獨立 commit;`npm test` 必須全過才能把任務改成 `review`。

## 4. 資料模型(檔案)
### 4.1 Project — `board/projects/<id>.json`
```json
{ "id": "ai-orchestrator", "name": "AI-Orchestrator", "path": "D:/MyProject/AI-Orchestrator",
  "defaultBranch": "main", "defaultPipeline": "standard", "worktrees": false }
```
`path` 必須是存在的絕對路徑;server 啟動時驗證,不合法的 project 標紅、不可派工。

### 4.2 Task — `board/tasks/<id>.md`(沿用,擴充 frontmatter)
新增可選欄位:`project`(project id)、`pipeline`(pipeline id)、`goal`、`acceptance`(驗收條件,`;` 分隔)。
舊任務沒有這些欄位時行為不變(向下相容,`project` 缺省 = 看板 repo 自己,並在 UI 顯示警告)。

### 4.3 Task 狀態
`draft → queued → running → needs-you → completed`,另有 `failed`、`cancelled`。
- `needs-you` = 等我核准計畫 / 審查失敗超過上限 / agent 提問 / 衝突。**首頁最優先顯示。**
- 舊欄位對應(Board View 用):backlog=draft、todo=queued、doing=running、review=needs-you、done=completed。
- 遷移:server 讀到舊 status 值時自動對映,不必一次改寫所有檔案。

### 4.4 Pipeline — `pipelines/<id>.json`
```json
{ "id": "standard", "maxRevisions": 3, "steps": [
  { "id": "plan",   "agent": "claude",  "mode": "plan",    "output": "plan.md",   "gate": "human" },
  { "id": "code",   "agent": "codex-a", "mode": "execute", "input": ["plan.md"] },
  { "id": "test",   "type": "command",  "command": "npm test" },
  { "id": "review", "agent": "gemini",  "mode": "review",  "input": ["plan.md","diff.patch"], "output": "review.md" },
  { "id": "revise", "agent": "codex-a", "mode": "execute", "when": "review.failed", "input": ["review.md"], "loopTo": "test" }
]}
```
- `gate: "human"`:該 step 完成後 run 進入 `needs-you`,**核准(或帶修改意見)後才進下一步**。預設 `standard` pipeline 的 plan step 一律有此 gate(= 計畫模式後才確認執行)。
- `mode`:`plan`(唯讀)/ `execute`(可改檔)/ `review`(唯讀)。
- review 結果約定:review agent 必須在 `review.md` 第一行寫 `VERDICT: PASS` 或 `VERDICT: FAIL`;引擎只解析這一行。
- 回修迴圈超過 `maxRevisions` → `needs-you`(選項:再試一次 / 我自己處理 / 忽略並完成)。
- 內建至少兩個 pipeline:`standard`(如上)、`single`(單一 agent,仍先 plan+gate 再 execute,可在 UI 關閉 gate)。

### 4.5 Run — `board/runs/<taskId>/<runId>/`
```
run.json          { runId, taskId, pipeline, status, steps:[{id,agent,mode,status,startedAt,endedAt,exitCode,pid}], ... }
events.jsonl      每行一個標準化事件(§5.2)
artifacts/        plan.md review.md diff.patch test.txt ...(step 之間的交接就靠這些檔)
raw/<stepId>.log  CLI 原始輸出(除錯用)
```
整個 `board/runs/` 已 gitignore。**舊的 `board/runs/<id>-<ts>.log` 與 `state.json` 在 WP3 遷移期間須相容或一次性遷移,不可默默丟資料。**

## 5. Agent Adapter(`tools/adapters/`)
### 5.1 介面
```js
// 每個 adapter 匯出:
export const id = 'claude';
export function buildCommand({ mode, prompt, cwd, agentCfg }) → { cmd, args, env }   // 純函式,可單元測試
export function parseLine(line) → Event | null                                      // 把該 CLI 的輸出行轉成標準事件
```
引擎(`tools/engine.mjs`)只依賴這個介面,不得出現 `if (agent.type === 'claude')` 之類的分支。

### 5.2 標準事件
`{ ts, runId, step, kind, text?, tool?, file?, exitCode? }`,`kind` ∈ `start | message | tool | file-edit | command | test | error | end`。
解析要寬鬆:未知行 → 存進 raw log,不丟例外。

### 5.3 三個 CLI 的旗標(已用本機 `--help` 核對,版本:claude 2.1.285 / codex 0.157.0 / gemini 0.58.0;升級後須重驗)
| mode | claude | codex (`exec`) | gemini |
|---|---|---|---|
| plan / review(唯讀) | `-p --permission-mode plan` | `-s read-only` | `-p --approval-mode plan` |
| execute | `-p --permission-mode acceptEdits` | `-s workspace-write`(或 `--full-auto`) | `-p --approval-mode auto_edit` |
| 結構化輸出 | `--output-format stream-json`(需搭配 `--verbose`,**實測確認**) | `--json`(JSONL) | `-o stream-json` |
| 工作目錄 | 以 spawn 的 `cwd` | `-C <dir>` | 以 spawn 的 `cwd` |
| 取最後回覆 | 從事件流 | `-o <file>` | 從事件流 |
### 實測結果(2026-09-30,WP2)
- **claude 2.1.285**:`-p --permission-mode plan --output-format stream-json --verbose` 實跑成功(NDJSON:system/assistant/rate_limit_event/result;result 含 `permission_denials`、`total_cost_usd`)。未單獨測「不帶 --verbose」。
- **codex 0.157.0**:`exec -s read-only --json --skip-git-repo-check -C <dir>` 實跑成功(JSONL:`item.completed`/`turn.completed`)。
- **gemini 0.58.0**:**實跑失敗**——`IneligibleTierError: UNSUPPORTED_CLIENT`(Gemini Code Assist for individuals 不再支援此 client,官方要求遷移 Antigravity),是帳號/服務層問題,非旗標問題。另發現:未信任資料夾會把 approval mode 強制降為 default(唯讀承諾失效),headless 須加 `--skip-trust` 或設 `GEMINI_CLI_TRUST_WORKSPACE=true`。gemini 的 parseLine 只有依記憶手寫的合成 fixture,**未驗證**。**在帳號問題解決前,不得把 gemini 排進預設 pipeline 的必要步驟。**
- 三個 CLI 的 execute 模式:只有 `buildCommand` args 單元測試,**未實跑**(留待 WP3 以暫存 repo 煙霧測試)。

**未實測的組合標為「待驗證」**:WP2 的第一件事是對每個 CLI 實跑一次確認上表,結果回寫本表。execute 模式若 CLI 因權限卡住(headless 沒人可按),要在事件裡偵測並轉為 `needs-you`,不可無限等待。

## 6. UI(`web/`)
- 首頁三區:左 Agents(狀態燈:idle/running)、中 任務列表(分頁:Needs you / Running / Queued / Completed)、右 Activity(最近事件)。頂部選 Project + 「＋新任務」。
- 「＋新任務」最少只填:做什麼、選 Project;pipeline 預設 `standard`。
- **Task Detail 頁**:pipeline 進度(哪步完成/進行/待)、目前正在做的事(最近事件)、Artifacts(plan.md/diff/review)、原始輸出可折疊、按鈕:核准計畫 / 退回並附意見 / 停止 / 重試 / 續跑。
- **計畫核准畫面**:顯示 plan.md、預計動到的檔案、風險;按鈕「核准執行」「退回修改」。
- 用量:主畫面僅留一條摘要;完整統計移到 Analytics 頁;任務詳情顯示該任務用量(沿用現有 `usageInRange`)。
- Kanban 保留為 Board View 分頁。

## 7. 工作包(WP)與順序
每個 WP = 一張 `board/tasks/v21-wp*.md`(含驗收條件)。**狀態以任務卡為準**,不另開進度表。

| WP | 內容 | 依賴 | 建議 owner | 對應缺口 |
|---|---|---|---|---|
| WP1 | Project 模型 + 任務 project/goal/acceptance 欄位 + 用 project.path 當 cwd + 新任務表單 | — | claude | G1 G4 |
| WP2 | Adapter 層 + 三 CLI 旗標實測 + 事件標準化(events.jsonl) | WP1 | claude | G3 |
| WP3 | Run 引擎 + pipeline JSON + **human gate(計畫核准)** + artifacts 交接 + 回修上限 + 停止/重試/續跑 + 舊 run 遷移 | WP2 | claude | G2 G5 G7 |
| WP4 | SSE 事件流 + Task Detail 頁 + 計畫核准畫面 | WP3 | codex-a(claude 設計驗收) | G3 G8 |
| WP5 | 首頁重做(三區、Needs you 優先、Board View、Analytics 分頁、Project 切換) | WP4 | codex-a 或 gemini | G8 |
| WP6 | git worktree 隔離 + diff.patch artifact + 合併流程 | WP3 | codex-b/codex-a | G6 |
| WP7 | Review agent 與 VERDICT 迴圈整合測試、Human intervention 三選項 | WP3 | claude | G5 |
| WP8 | 任務級用量整合進 Task Detail、Analytics | WP4 | gemini/任一 | — |

關鍵路徑 **WP1 → WP2 → WP3**,做完即達成「先計畫、確認後才執行」與「不再黑箱」的最低目標;WP4 起是體驗層。

## 8. 驗收總則(所有 WP)
1. `npm test` 全過;新行為要有測試(adapter 的 `buildCommand`/`parseLine` 用純函式測;引擎用假 CLI 腳本測,**不得在測試中呼叫真實 claude/codex/gemini**)。
2. 測試一律在暫存目錄隔離,**不得碰真實 `board/tasks/`、`board/projects/`**(見 `tests/server.test.mjs` 做法)。
3. 用真實 CLI 的煙霧測試由 WP owner 手動跑一次並把輸出摘要寫進任務卡 Log。
4. 完成後任務改 `review`,由使用者/Claude 驗收才 `done`。

## 10. 品質控管與返工規則(使用者 2026-09-30 指示)
1. **Claude(指揮官)是品質關卡**:任何 agent 交出的 WP 進 review 後,由 Claude 複核(跑 npm test、讀 diff、抽查行為)才算過;實作者自報完成不算數。
2. **有問題就退回同一個 agent CLI 返工**:把具體缺失寫進任務卡 Log(做錯什麼、預期什麼、怎麼驗證),狀態改回 todo 重新派給**原本那個 agent**,不要換人搶救(除非該 agent 連續 2 次失敗才換,並說明)。
3. **可選模型**:每個 agent 可選其 CLI 常用模型(如 codex 的不同 GPT 模型、claude sonnet/opus、agy 各 gemini-3.x 檔位)。任務或 step 可指定 model,優先序 step > task > agent.defaultModel > CLI 預設。見 WP10。
4. **agy(Antigravity CLI)取代 gemini CLI**:gemini 帳號不可用(UNSUPPORTED_CLIENT)。agy 非互動用 `-p='<prompt>'`(prompt 必須綁在旗標上),`--mode plan|accept-edits`、`--output-format stream-json`。見 WP9。
5. 為節省 Claude 額度:實作/測試/審查優先派給 codex 與 agy,Claude 只做決策、任務卡撰寫、複核。
